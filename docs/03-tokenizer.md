# 03　Tokenizer：文字怎麼變成數字

對應原始碼：`src/tokenizer.ts`

模型只會算數字。Tokenizer 負責兩件事：把文字切成一個個 **token**，再把每個 token 換成一個整數 id。反方向（id → 文字）則用來把模型的輸出變回人看得懂的字。

Tokenizer 不是神經網路的一部分，沒有梯度，也不參與訓練。但它決定了「模型眼中的最小單位」，影響非常大。

## 1. 該用什麼當作 token？

| 切法 | 例子 | 字表大小 | 問題 |
|------|------|----------|------|
| 字元 | `h` `e` `l` `l` `o` | 很小（英文約 100） | 序列很長；模型得自己學會拼字 |
| 單字 | `hello` `world` | 很大（數十萬） | 沒看過的字無法表示；`run`、`running` 被當成無關的兩個 token |
| 子詞（subword） | `runn` `ing` | 自訂（數萬） | 需要一套演算法決定怎麼切 |

這裡有一個根本的取捨，來自模型的兩個成本：

- **字表越大，模型的頭尾越貴。** Embedding 表有 `V × C` 個參數；輸出層要對每個位置算 `V` 個分數。本專案 `V = 2001` 時，embedding 表就佔了全部參數的 56%。
- **序列越長，中間越貴。** Attention 的計算量和序列長度的平方成正比，而且 context 長度有上限，token 切得越碎，能看到的內容就越少。

子詞切法是兩者的折衷，也是所有現代 LLM 的選擇。

## 2. 本專案的預設：`CharTokenizer`

對五言詩來說，一個字就是一個意義單位，字元級切法剛好非常自然：

```
春 眠 不 覺 曉 ，     →   [812, 1045, 37, 1688, 901, 2000]      （id 為示意）
```

實作只有一張對照表：把語料裡出現過的字排序、編號。唯一的設計細節是 **id 0 保留給結束符號 `<|end|>`**。

### 結束符號的用途

訓練時，每首詩的前後各放一個結束符號：

```
<|end|> 春 眠 不 覺 曉 ， …… 少 。 <|end|>
```

它同時扮演兩個角色：

- **開頭**：模型看到 `<|end|>` 就知道「接下來是一首新詩的第一個字」。生成時就是餵一個 `<|end|>` 讓它開始寫。
- **結尾**：模型要學會在句號之後預測 `<|end|>`。生成時抽到它就停下來。

少了它，模型不知道詩在哪裡結束，生成時會沒完沒了地寫下去。

### 字表外的字

`CharTokenizer` 遇到沒看過的字會直接報錯。這是字元級和單字級切法共同的弱點，也是下一節 BPE 要解決的問題。

資料準備階段（`scripts/prepare-data.ts`）刻意只保留最常見的 2000 個字，含有罕見字的詩整首丟掉。罕見字在語料中只出現幾次，模型根本學不到它的用法，卻要為它付出 embedding 表和輸出層的成本。

## 3. GPT 實際使用的做法：Byte Pair Encoding

BPE 的想法是：**不要人工決定怎麼切，讓資料自己告訴我們哪些東西常常黏在一起。**

### 3.1 訓練演算法

1. 把文字轉成 UTF-8 bytes。一開始每個 byte（0 到 255）就是一個 token。
2. 統計所有「相鄰的一對 token」各出現幾次。
3. 把出現最多次的那一對合併成一個新 token，分配下一個 id（從 256 開始）。
4. 重複步驟 2、3，直到字表大小達到目標。

### 3.2 手算一次

對字串 `aaabdaaabac` 做三次合併：

| 步驟 | 序列 | 最常見的 pair | 動作 |
|------|------|---------------|------|
| 初始 | `a a a b d a a a b a c` | `(a, a)` 出現 4 次 | 合併成 `Z` |
| 1 | `Z a b d Z a b a c` | `(Z, a)` 出現 2 次 | 合併成 `Y` |
| 2 | `Y b d Y b a c` | `(Y, b)` 出現 2 次 | 合併成 `X` |
| 3 | `X d X a c` | 沒有重複的 pair | 停止 |

11 個 token 壓縮成 5 個。學到的三條合併規則 `(a,a)→Z`、`(Z,a)→Y`、`(Y,b)→X` 就是這個 tokenizer 的全部內容。`tests/misc.test.ts` 裡有這個例子的第一步。

> 步驟 1 之後 `(Z, a)` 和 `(a, b)` 都出現 2 次。平手時本專案選先遇到的那一對，確保結果可重現。

### 3.3 編碼新的文字

拿到一段新文字時，照著訓練時的**順序**重新套用合併規則：

1. 把文字轉成 bytes。
2. 在所有相鄰的 pair 中，找「最早被學到」的那條規則（id 最小的），執行合併。
3. 重複，直到沒有任何 pair 符合規則。

順序很重要：`(Z, a)→Y` 這條規則必須在 `(a, a)→Z` 之後才有東西可以合併。先套用最早的規則，就能保證和訓練時的合併過程一致。

### 3.4 為什麼從 byte 開始

任何文字（中文、emoji、沒看過的語言）都能表示成 UTF-8 bytes。只要一開始的 256 個 byte 都在字表裡，**就不存在「字表外」這回事**：最差的情況也只是退回一個 byte 一個 token，序列變長而已。

對中文來說，一個字在 UTF-8 裡是 3 個 bytes。BPE 訓練初期的合併，其實是在「重新發現」哪 3 個 bytes 構成常用字；之後才開始把常一起出現的字合併成詞。這解釋了一個常見的觀察：在 GPT 這類模型裡，常見的中文字是 1 個 token，罕見字會被拆成 2 到 3 個。

測試中有一個例子直接驗證這件事：用重複的「春」訓練兩次合併後，「春」就從 3 個 token 變成 1 個。

### 3.5 試試看

```bash
pnpm train -- --data data/poems-small.txt --tokenizer bpe --vocab-size 600 --steps 500
```

訓練初期的生成樣本會出現一堆 `�`。那是模型把 bytes 接錯了，拼出不合法的 UTF-8。字元級 tokenizer 不會有這種現象，因為每個 token 本身就是完整的字。這也是一個很好的體會：用 BPE 時，模型連「怎麼拼出一個合法的字」都得從資料裡學。

## 4. Tokenizer 如何影響模型的行為

理解 tokenizer 之後，很多 LLM 的「怪癖」就說得通了：

- **為什麼 LLM 不擅長數一個英文單字裡有幾個字母？** 因為它看到的可能是 `straw` + `berry` 這樣的兩個 token，從來沒看過個別字母。
- **為什麼計費和 context 長度都用 token 算？** 因為模型的計算量取決於 token 數，不是字數。
- **為什麼同樣的內容，中文通常比英文花更多 token？** 英文常見單字多半是 1 個 token，中文平均每個字 1 個以上。
- **為什麼換一個模型，tokenizer 通常不能沿用？** Embedding 表的每一列對應一個特定的 token id。換了 tokenizer，id 的意義就全變了。

## 重點回顧

- Token 是模型處理文字的最小單位；tokenizer 把文字和整數 id 互相轉換。
- 字表大小與序列長度互相拉扯；子詞切法是折衷。
- 結束符號讓模型知道文件從哪裡開始、在哪裡結束。
- BPE 反覆合併最常相鄰的一對 token。從 byte 出發，所以任何文字都能編碼。
